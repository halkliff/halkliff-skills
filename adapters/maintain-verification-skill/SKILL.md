# Maintain a verification skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `/create-verification-skill` (or any project-local verification skill with a feature map). The unit of rigor is the feature, not every sentence: cover every feature file from source and exercise every feature live, without terminalising every bullet.

An audit or review request is read-only; report proposed corrections. A request to maintain or repair the verifier authorizes edits only in its own directory. Use available Codex tools and workers, not Cursor-specific agent types or assumed shell programs. Preserve the user's dirty files, frozen journeys, and expected results. Commits, publication, remote CI, external writes, new chats, and recurring schedules require their own authorization.

## Outcomes

Pick one, and say which:

- **clean**: every mapped feature received source and live coverage; no corrections needed.
- **changed**: authorized corrections to the verifier or map are locally verified and ready for review. No automatic commit or PR.
- **findings**: a read-only audit found corrections or product gaps; no edits applied.
- **blocked**: required coverage or verification could not finish. Name the unmet prerequisite and partial evidence; do not count it as a pass.

A documented unreachable path is not live coverage. Keep the run partial or blocked while required paths remain unexercised, unless the user explicitly accepts a narrower coverage scope.

## Edit scope

For authorized maintenance, edit only the verification skill's own directory: its SKILL.md, features/, and owned helpers. Read `skill-creator` and `writing-for-agents` before changing instructions, and `test-audit` when changing tests. If the app differs from the map, establish the accepted contract before calling it documentation drift. Report product regressions; do not change product code or rewrite expected behavior to conceal them. A behavior-changing contract decision belongs to the user.

## Pass

0. **Locate the target.** Find the existing project-local verifier with launch/drive sections and a feature map. New Codex repository skills normally live under `.agents/skills/verify-*/`; preserve the project's established supported location. If several targets plausibly fit, ask which one. If none exists, point at [create-verification-skill](../create-verification-skill/SKILL.md) rather than inventing a target during maintenance.

1. **Index hygiene.** Read the feature map index and list its sibling files with native file tools or `rg --files`. Identify missing, duplicate, or dead entries. Apply corrections only when edits were requested; an audit records findings.

2. **Source wave.** Inspect every feature file against its actual source entry points. Use bounded read-only workers for independent features when available and authorized, batching related features to fit runtime capacity; otherwise inspect them directly. Workers never drive a shared instance or edit files. Return a feature summary, source citations, likely drift or none, and a concise live recipe. Distinguish source-derived expectations from behavior actually observed.

3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; don't re-prove clean claims. Sweep recent churn for user-facing surfaces missing from the map — require a concrete source path before calling one missing.

4. **Live pass.** Required even when source looks clean. The coordinator owns all driving; follow the verification skill's own launch model — one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs (the skill's Launch section decides, not this one). Exercise every feature at least once, and hold three invariants the whole pass, whatever the failure: (1) never drive an instance you haven't health-checked since it last did something surprising — doctor before first drive, doctor on each fresh session where sessions are the unit, doctor again after any failed drive, and where doctor can't see the failure (a wedged UI state on a healthy process), reset to a known state or relaunch rather than hoping; (2) evidence captured so far survives every cleanup, checked at its named location, not assumed; (3) nothing a drive started outlives that drive's usefulness — failed-iteration residue is cleaned whether the session is stuck, exited, or shared (for a shared instance, clean the residue, not the instance). A doctor failure caused by skill drift is drift: fix it under edit scope and retry once — restart whatever the fix invalidated, nothing more — before calling the pass `blocked`. A feature that can't be reached is `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route attempted; if the map omits that prerequisite, that's drift. Any harness fix from triage gets re-driven live before it ships. Final teardown happens after the last drive of the run — including those re-proofs — so nothing outlives the run (evidence stays, per the skill).

5. **Triage.** Wrong or missing user-POV description → doc drift, fix it. Working behavior the harness can't drive → harness gap, fix it; a harness fix follows the same helpers rule as generation (scripts executable, invocation documented in the skill body). App behavior that's actually broken → product gap; record it for the user, keep it out of this PR.

6. **Hand off or stop.** Re-read changed files, validate the skill and resource links, and re-drive every corrected helper before calling maintenance verified. Report the outcome, source and live coverage separately, unattempted or unreachable entry points, product gaps, exact evidence locations, and remaining work. Commit or publish only if explicitly requested; never schedule another run implicitly.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location; don't commit them.
